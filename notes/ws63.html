02七条踩坑记录

01 TM1637 根本不是标准 I2C

现象拿标准 I2C 库去驱动 TM1637，时序全对、地址也对，数码管一个字都不亮。

根因TM1637 只是"长得像 I2C"：它有起始/停止条件，但每个字节是从最低位开始传的（LSB first），而标准 I2C 是最高位优先（MSB first）。顺序反了，从设备收到的就是整字节位镜像的垃圾数据。

解法老老实实写两套位操作函数——一套给标准 I2C 的 PCA9535，一套给 TM1637，两者只差判断位和移位方向那一行。ACK 检测也必须做：发完 8 位要把 SDA 切成输入去读应答，读完再切回输出。

/* 标准 I2C：MSB 优先（给 PCA9535） */
if (data & 0x80) SDA_HIGH(); else SDA_LOW();
data <<= 1;

/* TM1637：LSB 优先，只有这两行不一样 */
if (data & 0x01) SDA_HIGH(); else SDA_LOW();
data >>= 1;

/* 读 ACK：SDA 必须先切输入，否则主从对着拉电平 */
uapi_gpio_set_dir(I2C_SDA, GPIO_DIRECTION_INPUT);
uapi_gpio_set_dir(I2C_SDA, GPIO_DIRECTION_OUTPUT);
02 两个从设备挤一条总线，得靠片选分时复用

现象数码管一刷新，8×8 点阵就停在那儿不动了；点阵一扫，数码管又开始闪。

根因板子上 TM1637 和 PCA9535 共用同一组 SDA/SCL 引脚。它们是两个独立器件，同时挂在一条总线上会互相抢线，谁都收不到正确数据。

解法用 GPIO09 当片选：写数码管前拉高，把总线交给它；写完拉低，还给点阵继续扫描。代价是每次刷新显示都要"切过去—写完—切回来"，所以主循环里的点阵扫描必须足够快，不然切回来的瞬间会看到一行残影。

static void tm1637_display_raw(uint8_t d1, uint8_t d2, uint8_t d3, uint8_t d4, uint8_t dot)
{
    selector_tm1637();      /* PIN9 = HIGH，总线交给数码管 */

    i2c_start();
    i2c_write_byte_lsb(0x40);   /* 自动地址累加 */
    i2c_stop();

    i2c_start();
    i2c_write_byte_lsb(0xC0);   /* 从第 1 位开始写 */
    /* ... 写 4 个段码 ... */
    i2c_stop();

    selector_matrix();      /* PIN9 = LOW，还给点阵 */
}
03 DHT11 没有时钟线，全靠脉宽自己数

现象读十次能有三四次校验和不通过，数据是乱码。

根因DHT11 是单总线协议：主机拉低 20 ms 起始，然后从设备用高电平的持续时间表示 0 和 1——约 26–28 μs 是 0，约 70 μs 是 1。判定点取在 30 μs 处：这时候还是高电平就是 1，已经掉下去就是 0。任何一个中断插进来打乱这几微秒，整个字节就废了。

解法每个等待循环都带超时计数，超了就立刻返回失败、放弃这一轮，绝不空等。传感器读失败只是显示"--"，不能让整个任务卡死在等电平上。

static int dht11_read_byte(uint8_t *byte)
{
    uint8_t data = 0;
    for (int i = 0; i < 8; i++) {

        uint32_t timeout = 1000;
        while (dht11_pin_read() == 0) {      /* 等 50μs 低电平结束 */
            if (--timeout == 0) return -1;      /* 超时保护，不死等 */
            DHT11_DELAY_US(1);
        }

        DHT11_DELAY_US(30);                  /* 30μs 采样点：0 和 1 的分界 */
        data <<= 1;
        if (dht11_pin_read() == 1) data |= 0x01;
        /* ... 再等它掉下去 ... */
    }
    *byte = data;
    return 0;
}
04 SDK 只给毫秒睡眠，微秒延时得自己空转

现象DHT11 要 30 μs 级精度，但 SDK 里只有 osal_msleep()，最小粒度就是 1 ms——差三个数量级。

根因RTOS 的睡眠会主动让出 CPU 触发任务调度，唤醒时间受调度器影响，压根不可能精确到微秒。这种场合不能用"睡"，只能"忙等"。

解法用 nop 空转拼出微秒延时。代价是延时精度绑死主频——上面那个 ×50 的系数是在当前主频下试出来的，换主频就得重算，否则 DHT11 立刻读不出数据。这是整个项目里最"硬编码"、也最需要注释的一行。

static void delay_us(uint32_t us)
{
    for (uint32_t i = 0; i < us * 50; i++) {
        __asm__ volatile ("nop");   /* 50 次 nop ≈ 1μs，依赖主频 */
    }
}
05 光控开关在阈值附近疯狂闪烁

现象环境光刚好停在临界值时，照明灯开始高频开关，肉眼看着像在抽搐。

根因单阈值比较没有"记忆"：读数一旦在阈值上下抖动，条件就反复成立、反复翻转。真实世界的模拟量在临界点附近必然是抖的，这是必然事件不是偶然。

解法加滞回带——开灯阈值定在 500 mV，关灯阈值定在 800 mV，中间留 300 mV 的死区。灯一亮就要等环境明显变亮才关，反之亦然，抖动被这 300 mV 吃掉了。

/* 开和关用两个不同的阈值，中间那条缝就是滞回带 */
#define LIGHT_THRESHOLD_ON   500   /* 低于此值：开灯 */
#define LIGHT_THRESHOLD_OFF  800   /* 高于此值：关灯 */

if (g_light_on) {
    if (g_light_mv > LIGHT_THRESHOLD_OFF) led_light_set(false);
} else {
    if (g_light_mv < LIGHT_THRESHOLD_ON)  led_light_set(true);
}
06 数码管想显示字母，段码得自己拼

现象温度显示想带单位 "°C"、湿度带 "%RH"、光照带 "LUX"，但段码表里只有 0–9 十个数字。

根因七段数码管只有 a–g 七根笔画，标准段码表只覆盖数字。字母必须手工挑出"哪几段亮起来最像这个字母"，没有现成表可查。

解法按笔画位置反推。C 是 a、d、e、f 四段（缺右上那段竖）→ 0x39；H 是 b、c、e、f、g → 0x76；L 是 d、e、f → 0x38。拼错一位，显示出来就是另一个字母，只能一个个试。

/* 0-9 是标准共阴极段码 */
static const uint8_t seg_table[] = {
    0x3F, 0x06, 0x5B, 0x4F, 0x66, 0x6D, 0x7D, 0x07, 0x7F, 0x6F,
    0x00, 0x40   /* 空格、横杠（传感器失败时显示 --） */
};

/* 单位符号：按笔画位置手工拼出来的 */
#define SEG_UNIT_C  0x39   /* a d e f      → C */
#define SEG_UNIT_H  0x76   /* b c e f g    → H */
#define SEG_UNIT_L  0x38   /* d e f        → L */
07 看门狗是"喂"的，不是"重置"的

现象程序跑着跑着整机重启，日志从开机横幅开始重新打印。

根因主循环里点阵扫描是纯耗时操作，一旦某次循环超过看门狗的超时窗口，芯片就认为程序跑飞了，直接硬复位。

解法在循环里定期"喂狗"。SDK 没有单独的 feed 接口，实际做法是 disable + enable 组合——重新使能等于把计数器清零。放在每 100 帧点阵扫描之后，既不会太频繁浪费 CPU，也不会漏掉。

static void feed_watchdog(void)
{
    uapi_watchdog_disable();
    uapi_watchdog_enable(0);   /* 重新使能 = 计数器归零 */
}

/* 主循环里：攒够 100 帧点阵扫描就喂一次 */
frame_count++;
if (frame_count >= 100) {
    frame_count = 0;
    feed_watchdog();
}

04线程模型

整个程序是一个单任务大循环，不是多线程。入口 app_run() 创建唯一一个任务，之后所有事情——点阵扫描、传感器采样、显示刷新、按键、喂狗——都按各自的时间片在这个循环里轮转。

时间基准统一用 osal_get_jiffies() × 10 换算成毫秒，然后各自比较"距上次执行过了多久"，而不是用阻塞式睡眠。这样任何一个环节慢了，也不会连累其它环节的节奏。

while (1) {
    matrix_scan_frame();                        /* 每轮都扫，保证点阵不闪 */

    if ((now - sensor_tick) >= 2000) {        /* 传感器：2s 一次 */
        sensor_sample();
        check_alarm();
        light_control();
    }
    if ((now - disp_tick) >= 200) {           /* 数码管：200ms 一次 */
        update_display();
    }
    alarm_led_update();                         /* 报警灯闪烁 */
    process_key();                               /* 按键消抖 */
}

任务句柄创建完立刻 osal_kfree() 释放——任务本身继续在跑，只是不再持有这个句柄，省下一份内存。

05后续：项目扩成气象站，DHT11 突然全读失败

同一个 DHT11、同一段单总线时序，在检测站里好好的；换成气象站项目后读数恒为失败。没有示波器和逻辑分析仪，最后靠纯软件自检把接线位置反推了出来。

01 现象：网络全绿，唯独本地读数恒失败

现象串口里 WiFi、MQTT、网络天气全部正常，只有 DHT11 每次读都失败；上报 JSON 里 local_ok 恒为 0，而 net_ok 恒为 1。链路没问题，坏的是这一根单总线。

先做减法与其反复改代码，不如先把失败点切开：给读取函数加分阶段日志，区分「从机无应答 / 应答电平异常 / 数据位超时 / 校验和错误」，并打印采样前总线的空闲电平。结果稳定停在应答阶段，且空闲电平是 0——但代码已经开了内部强上拉，空闲时本该被拉回 1。

02 手段：把引脚拉低再释放，看它能不能自己弹回来

「空闲电平为 0」有两种可能：线根本没接到这根引脚（悬空），或者这根引脚被板上的东西强行拉低。分不清这两种，就换不到对的引脚。于是写了个自检：把引脚拉低，再释放成高阻输入，读回电平。

线若真挂在带上拉的传感器上，它会自己弹回高电平；若悬空或被人拉死，就还是低。关键前提：DHT11 模组自带 4.7k 上拉——所以「它插在哪根针上，那根针必被拉高」，用这个特征就能反推接线位置。

/* 判定某个引脚上是否真的挂着带上拉的传感器 */
static int line_present(pin_t p)
{
    uapi_pin_set_mode(p, HAL_PIN_MODE_GPIO);
    uapi_gpio_set_dir(p, GPIO_DIRECTION_OUTPUT);
    uapi_gpio_set_val(p, 0);                  /* 先拉到低 */
    uapi_gpio_set_dir(p, GPIO_DIRECTION_INPUT);   /* 再释放 */
    return uapi_gpio_get_val(p);             /* 弹回 1 => 线上有东西 */
}

结果把板上几根候选脚全扫一遍：只有 GPIO10 读回 1（另外两根是板载 TM1637 自己的线）。数据线的实际位置，就这么被试出来了。

03 根因与解法：同一个引脚，被两件事同时用

根因数据线在 GPIO10，而程序里 GPIO10 正好被当成状态 LED 的输出脚，默认输出低电平——等于把 DHT11 的总线一直按在地上，从机再想拉高应答也拉不起来。这也解释了为什么「代码没怎么改、只是换了项目」就坏了：引脚分配一变，冲突才暴露。

另一处坑气象站要用数码管，而板载显示选择器占着 GPIO02，原本 DHT11 就接在 GPIO02 上。程序一旦把选择器驱动成低电平，这根线同样会被拉死——所以 DHT11 必须换到空闲引脚。

解法把两件事拆开：DHT11 用 GPIO10，LED 挪到空闲的 GPIO12，冲突消失，而且一根线都不用动。所有引脚集中写在一张分配表里，谁占哪根一眼可见。

事后总结：嵌入式里的「代码问题」经常是接线问题，而接线问题可以被软件逼问出来——拉低、释放、回读，三步就能把一根引脚上的真相问清楚。
